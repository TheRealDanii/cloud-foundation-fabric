- **Endpoints, not load balancers, and the networking stage owns them** (2026-11-04). The template exposes the two service attachments and creates nothing in front of them; each consumer VPC gets two PSC endpoints (one per attachment, since a PSC forwarding rule has no ports) declared as `addresses.psc` in the networking stage, naming the attachments through a new `service_attachments` context key added to `net-address` and the stage (`e7ab0cc77`). DNS becomes per VPC. The load balancer pair stays in the README as the answer for clients behind a peering, which in this playground is the build workers; `ssm-load-balancers.tf`, the shared VIP and the `network_config.subnetwork` input are gone and the plan drops from 50 to 39.

- **Repositories and the identity chain are written** (2026-11-04). One variable, `repositories_config`, rather than separate repository and identity maps: build identities are per repository in practice (`ro` and `rw`, mirroring the stage accounts they impersonate), so nesting them removes a cross-map validation and reads straight off the YAML; a shared identity, should one ever be needed, is one optional reference attribute later. `ssm-repositories.tf` creates one BYOSA per repository with the service agent's `tokenCreator` from `module.ssm-project`, `serviceAccountUser` on exactly that repository's identities, and the three Cloud Build roles on the build project; `module.build-sa` is keyed `<repository>/<identity>`, named `<repository>-<identity>` under the prefix, and carries `logWriter`, `workerPoolUser`, `privateca.auditor` on the CA project and `tokenCreator` on each `impersonate_service_accounts` entry. `ssm-instance.tf` passes the repositories with `service_account`, `repoReader` per identity on the repository, and `instanceAccessor` for all identities on the instance. `build-sa-test` is gone; its two probe builds now name `test-0-test-ro`. Plans at 31 resources from the empty state.

- **Impersonation of stage accounts is granted from here, under a per-account delegation in the bootstrap stage** (2026-11-04). Reverses the September decision that put the `tokenCreator` binding in stage 0 as static context: both ends of the edge are known in this configuration, and a delegation on the account resource (custom role with only the policy permissions, conditioned to `tokenCreator`) lets the account's owner declare which accounts may be impersonated at all, which is a smaller blast radius than either a project-level delegation or an unconditioned grant. README, delegation section, including why `roles/iam.serviceAccountAdmin` cannot be the delegated role.

- **The SSM service agent comes from a reused `project` module** (2026-09-15, project inputs reshaped 2026-09-16). `module.ssm-project` in `main.tf` reuses the factory's instance project and creates nothing; `service_agents["sourcemanager"].iam_email` resolves to `serviceAccount:service-169822929449@gcp-sa-sourcemanager.iam.gserviceaccount.com` with no API call and no plan diff. Two things about it are not obvious and are written down in the comment there: the data source path cannot be used, because `services_enabled` lives under `project_reuse.attributes` and an agent is not derived at all for a service the module has not been told about; and `service_agents_config` must switch off agent creation and default roles, or the same IAM members end up owned by this state and the factory's. The project id and number both come in through `projects_config.ssm`; the build project is `projects_config.build` and falls back to the instance project when null, via `local.build_project`. The earlier top-level `number` variable, which mirrored the factory tfvars key, is gone: it was no longer read and only planned because the symlinked tfvars happened to carry it.

## Follow-up, outside this template

- **PSC NEG backends and balancing mode — closed, no module work** (2026-09-13). The apply failure here came from this template passing `balancing_mode = "CONNECTION"`, not from a module defect. Probed live against the API: a PSC NEG backend accepts `UTILIZATION` and rejects `CONNECTION` and `RATE` ("Balancing mode is not supported for Private Service Connect network endpoint groups"); omitting the mode is accepted and the server stores `UTILIZATION` itself. All six PSC-capable modules default to `UTILIZATION` except `net-lb-proxy-int-cross-region`, and every one of them lets a caller set it, so each has a reachable valid configuration. Fixed here by dropping the override. Global backend services could not be probed: they reject the backend before reaching the mode, needing a producer with `AllowGlobalAccess`. The pickup note that held the probe tables was deleted with the finding, since the finding is the whole of what it was for.

- **Publish CA bundles to a bucket instead of granting read on the CA.** Rough shape, not validated. `modules/certificate-authority-service` already takes `ca_configs.<ca>.gcs_bucket`, resolved through a `storage_buckets` context key, and `ca_pool_config.create_pool.publishing_options` with `publish_ca_cert` and `publish_crl`. The 2-security stage does not carry it: `context` in `defaults.schema.json` has no `storage_buckets` key, so a bucket cannot be named symbolically from a CA definition, and nothing anywhere handles a managed folder to scope access to one bundle rather than a whole bucket. With this, a consumer reads the chain from the folder and needs no role on the CA project at all, which removes both the per-identity grant and the delegation that enables it. The cost is a published artifact that has to stay current across CA rotation, against a live fetch that cannot go stale.

- **IAM conditions on the SSM module.** `iam_bindings` and `iam_bindings_additive` carry no `condition` and all three IAM variables share the description `"IAM bindings."`. Module surface, not provider lag, and Fabric's standard interfaces are a promise. Nothing here waits on it; a different branch.
- **`requiredStatusChecks` and `requireCodeOwnerApproval` on branch rules.** The REST resource has both, `BranchRule.yaml` in Magic Modules has neither. Contribute upstream, then add to the module. Until then both are set in the web interface and the README's security note says so.
